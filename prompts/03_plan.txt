【任务】
将通过审查的意图展开为信息关系图、用户请求和文件构建计划。

【输入】
读取 task_id、intent、constraints，以及可选的 source_materials 原始来源正文。真实来源只支持其中明确可见的事实，保持机构和时间范围一致。constraints 指定合成权限、文件格式、外部资源和工具条件。

【执行规则】
参考文件数量与格式由信息角色、专业场景及实际工具能力决定。没有明确数量约束时不得固定两份或为了接近统计均值拆分材料。空的 allowed_reference_formats 表示不限定格式。可组合数据表、PDF 报价、DOCX 条款、PPTX 背景资料等，但只安排有业务作用的文件。交付物格式按工作目标规划。
从交付物倒推必要计算、判断及支撑信息。每个信息节点标明实体、范围、单位、提供状态和来源。同结构多条记录合并为一个表级节点，在 value 或 construction_spec 中描述，不为每条记录的每个字段重复建节点。每个节点绑定载体；载体区分 request、reference、external、deliverable、internal。信息提供状态使用 supplied、external、derived、internal。
relations 记录共同支撑目标的源节点、目标节点及关系。derived 仅描述待求结果，value 和 construction_spec 均为 null。公开的交付要求属于 supplied，待生成的报告或分析属于 derived。internal 仅用于隐藏构建说明，value 和 construction_spec 均为 null，不承载求解必需的事实或要求。
supplied 节点在 value 中填已确定的值，或在 construction_spec 中写待构建材料的完整生成要求，二者恰好填一项。后者必须明确字段、记录数量、时间单位及约束，不能用“有十条数据”冒充实际记录。标明哪些内容来自输入、哪些由授权合成。缺少授权或必要来源时返回 blocked。必要业务规则必须确定；所有求解前提和要求均安排到可访问输入。文件依赖限于参考文件且无环。交付物不预生成。
跨表关联必须在两侧明确安排共有的稳定键；待核对的金额、币种等差异字段不能作为唯一匹配依据。计算依赖的日历、截止时点及缺失值处理须在输入中明确，不得依赖未提供的外部口径。
约束指定的请求文件路径须在 user_request 和 request 载体中一致使用；REQUEST.txt 位于工作区根目录，不能写为 inputs/REQUEST.txt，也不能规划重复副本。
合成权限仅用于环境构建，用户请求要求依据已提供材料求解，不授权求解者编造缺失事实。技能卡中的名称仅表示工作能力；只有环境明确提供的工具才可要求按名称调用。即使 intent 提到技能名，user_request 也必须改写为业务动作。例如把“用 invoice_extract 提取发票”写成“提取发票明细并保留来源位置”。

【输出格式】
只返回符合所附输出结构的一个 JSON 对象。第一个字符必须为 {，最后一个字符必须为 }，禁止 Markdown 代码围栏和对象外说明。输出使用稳定的节点及文件 ID；无依赖用空数组。必要资源缺失用 blocked，并指出具体缺项。

【验收要求】
每项交付物要求有对应信息节点；每个派生结果有支持关系；所有引用存在；可见节点具有可见载体；用户请求覆盖业务规则和成果要求；不暴露求解结果。
